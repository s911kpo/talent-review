新店廠 122 人的規模，離系統上限還很遠；擴大到多廠區數千人也不需要改架構。

## 1. 資料庫（`npm run test:stress`）

以 PGlite（WebAssembly 版 Postgres，通常比雲端慢數倍）模擬 5,001 人、368 位評核人、1,477 筆評核、3 個週期。

| 動作 | 毫秒 |
|---|---|
| HR 上傳 5,000 人名單（每個週期） | 218–268 |
| HR 讀取整個週期的評核 | 4 |
| HR 總覽（368 位評核人） | 104 |
| 全廠平均 | 62 |
| 廠長的整條組織線（遞迴，跨 3 個週期） | 31 |
| 廠長依權限讀取評核 | 58 |
| 課級主管依權限讀取（數千筆中只看到自己的） | 16 |
| 自動存檔 p50 / p95 | 36 / 39 |

權限在這個規模下仍然正確：廠長只看到下屬主管「已提交以後」的內容，課級主管只看到自己的團隊。

注意：自動存檔時間隨評核總數增加（600 人時 10 毫秒、5,000 人時 36 毫秒）。到 5 萬筆評核以前都不需要處理。

## 2. 畫面（`npm run test:stress:ui`）

以 5,000 人的示範模式，用無頭瀏覽器實際操作 HR 後台。

| 動作 | 毫秒 |
|---|---|
| 登入到總覽表 | 299 |
| 開啟戰略儀表板 | 454 |
| 切換分頁 | 72–320 |
| 部門篩選 | 34 |
| 下鑽到人員清單 | 278 |

**大規模時發現並修正的畫面問題**
- 「單點失效清單」一次列出全部人名（600 人時已有 33 人），整頁被拉得很長 → 改為先顯示 8 位，加「查看全部」。
- 「接班網絡圖」在數百個職位時變成無法閱讀的線團 → 超過 30 個職位時改為依部門顯示。
- 評核人篩選出現同名的人 → 同名時加上工號。真實組織也會遇到同名。

## 3. 真實 Supabase 同時負載（`node scripts/load-remote.mjs`）

模擬最忙的情況：11 位示範主管同時登入、每人連續存檔 40 次，同時 HR 重新整理儀表板 20 次。測試結束時自動刪除產生的資料，並以 `verify-remote` 確認 19 項權限檢查仍然全部通過。

| 動作 | p50 | p95 | 最大 |
|---|---|---|---|
| PIN 登入 | 1.4 秒 | 2.0 秒 | 2.0 秒 |
| 自動存檔 | 0.15 秒 | 0.18 秒 | 0.35 秒 |
| HR 儀表板（20 個同時） | 1.5 秒 | 3.5 秒 | 3.5 秒 |

登入較慢是因為 Edge Function 需要冷啟動，以及從台灣經過公司網路連到新加坡。主管實際使用時，存檔在背景進行，不會感覺到。

## 4. 報錯情境（`npm run test:resilience`）

對真實後端，在瀏覽器中模擬網路與伺服器故障。

| 情境 | 結果 |
|---|---|
| 登入服務故障 | 顯示「目前無法登入，請稍後再試」，恢復後可登入 |
| 存檔時伺服器錯誤 | 顯示「儲存失敗，正在重試」，伺服器恢復後自動存好 |
| 斷線 | 顯示「目前離線，內容暫存在此裝置」，連線後自動送出 |
| 兩台裝置同時編輯 | 偵測到衝突並要求重新載入，不會覆蓋 |
| **登入逾時** | **原本會每 5 秒重試、永遠不停，也不告訴主管。已修正**：改為提示「登入已逾時」，內容保留在裝置上，重新登入後自動送出 |
| **編輯途中 HR 鎖定團隊** | **原本同樣會無限重試。已修正**：改為說明「已提交或鎖定」，並提示可以申請修改 |
| 儀表板讀取失敗 | 顯示「發生錯誤」與重試按鈕，重試後恢復 |
| 網路很慢（4 秒） | 顯示「儲存中…」，不會重複送出 |

所有錯誤畫面都檢查過：不會出現技術訊息（例如 JWT、錯誤代碼、程式堆疊）。

## 怎麼重跑

```
npm run test:stress          # 資料庫與計算，5,000 人（約 1 分鐘）
npm run test:stress:ui       # 畫面，5,000 人
npm run test:resilience      # 報錯情境，需要 .env.local，會連到 Supabase
node scripts/load-remote.mjs # 同時負載，需要 .env.local
```

在公司電腦上執行後兩項時，要先設定 `NODE_USE_ENV_PROXY=1`。
